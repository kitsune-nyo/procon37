# fix: ビームサーチの状態管理と役割決定の不具合を修正

## 1. 概要

役割候補・探索候補の状態混入、更新後の評価漏れ、移動中・最終ステップの不整合を修正します。期限が近い場合は開始済み移動を完了し、残りを待機で埋めた有効な計画を提出します。

最大ビーム幅3000、補給車数N/3～N/2の探索範囲、目的地の候補、評価重みを維持します。`json.hpp` と `spot.cpp` は変更しません。

## 2. 修正前に存在した問題

- `agentsKind()` がAgentManagerを使い回し、前候補の補給車が残っていました。`decideSupply()` の二重指定も台数を変更していました。ビット列は末尾0を省略していました。
- `collectUdon()` が探索全体で共有したbrandsを変更し、未採用の未来の取得が他候補と翌日の評価に混入していました。
- `update()` 後に再評価せずキューへ戻し、位置・燃料・取得結果がscoreに反映されていませんでした。intのscoreでは平均燃料等の小数も失われていました。
- 移動中にactionsが空だと状態を進められず、移動元から生成した新しい経路は到着後に不正な移動を予約しえました。
- 最終ステップの移動反映が欠落し、0ステップと取得・補給の処理時点も公式Q6と一致していませんでした。DIR_TABLEの偶奇行は公式Q1と逆でした。
- 時間調整だけでは予算内に探索を中断できず、HTTP 200の負のrevisionを不受理として扱っていませんでした。

## 3. 変更内容

| ファイル | 変更と理由 |
|---|---|
| `agent.cpp` | 補給指定を冪等化し、kindと台数を一致させる |
| `state.cpp` | 候補内のブランドだけを更新し、評価で過去日との和集合を数える。scoreをdouble化。移動中の更新を許可し、到着後に新経路を生成。公式順に最終反映まで処理。不正方向・池・燃料不足の移動を抑止 |
| `map.cpp` | 偶数行が右へずれる公式配置へ修正。範囲外座標と前計算中の期限切れを検出 |
| `hexudon_main.cpp` | 固定桁の役割列挙、独立した役割候補、初期・更新後の評価。前計算・探索の期限確認と待機での計画完成。endsAtを基準にGET・準備時間を差し引き、POST timeoutも制限。revision>=0の計画のブランドだけを引き継ぐ。重複した外部json includeを除去 |
| `tests/` / `REVIEW.md` | 再現テスト、公式行動再生・サーバー検証、呼び出し関係・根拠・未確認事項を追加 |

公式の移動元の地形コスト、日ごとの在庫補充・訪問履歴リセットは既存実装が正しいため維持します。公式日次情報にブランド実績はなく、位置・燃料は公式入力を優先し、ブランドは受理された計画の再生結果だけを保持します。

根拠: [公式Q6行動詳細](https://www.procon.gr.jp/uploads/download/BcAnkz3QVAA)、[Q&Aその1](https://www.procon.gr.jp/uploads/download/BcAnkyvgVAA)、[フォーマット](https://www.procon.gr.jp/uploads/download/BcgL66tAVAA)、[公式簡易サーバーとAPI](https://www.procon.gr.jp/news/2026/08/20/117)。資料別の該当項目は `REVIEW.md` に記載しています。

## 4. 問題の再現方法

修正前の6ファイルを別フォルダへ保存し、次を実行します。修正版のテストは成功し、原本のstate / roles / solver / officialの各モードでは失敗が再現されます。

```sh
python tests/run_tests.py --baseline-dir /path/to/original
```

Windowsでlibcurlの開発ファイルを別途配置している場合は `--curl-root` を指定します。公式サーバー検証は `--official-server` に配布バイナリを指定します。

```powershell
python tests/run_tests.py --curl-root 'C:\path\curl-8.22.0_3-win64-mingw' --baseline-dir 'C:\path\original' --official-server 'C:\path\procon-server-windows-amd64.exe'
```

最小ケースには、同じ1台への二重補給指定、A/BのうちAだけのブランド取得、平地0→1の移動予約中の空キュー、非隣接0→2の予約、燃料0からの移動、2ステップ目ちょうどの到着、公式Q6の8台例を含めています。

## 5. テスト結果

- GCC 15.1.0、C++17、`-O2` で本体・テストドライバーをコンパイル。`-D_GLIBCXX_ASSERTIONS` の回帰も成功。
- 修正前は13件の失敗を再現、修正版は全回帰モード成功。
- N=3～8の全273役割候補で、桁数・重複・探索範囲・kind/カウンタ/合計一致を確認。
- 候補間の在庫・履歴・ブランド分離、最新評価、低評価候補の削除、小数評価、移動中・最終反映・燃料・方向を確認。
- 公式Q6例の位置・燃料・取得4玉・ID順が一致。独立した行動再生で全日分のステップ数と取得を検査。
- HTTPのURL・token・Content-Type・提出配列を維持。200/負revision、HTTP 400、50ms timeoutを検査。
- 公式簡易サーバーでは修正前の計画は不受理、修正版は2日とも受理。翌日の位置・燃料が独立再生と一致。
- 実際のmainでも2秒×2日の試合を行い、役割と両日の行動を期限内に受理。
- `json.hpp` と `spot.cpp` のSHA-256が原本と一致。

## 6. 競技性能への影響

同一8×8・32ステップ・探索予算0.5秒の単回測定は、原本1.431330秒、修正版0.556595秒でした。中断の導入による時間差であり、探索速度・勝率の改善を示すものではありません。修正前の得点は不受理計画上の値なので比較対象にできません。

正常時の幅調整・候補・重みは維持します。再評価の計算は増えます。中断時は選択した途中の計画を待機で完成させるため、深い探索より取得数が少なくなる場合があります。後処理の時間超過も観測したため、65%の探索割合とHTTP用の余裕を維持します。

## 7. 未修正・未確認事項

- 評価重みは公式の勝敗順を厳密に表現していません（2種類2玉より1種類8玉が高評価）。戦略変更になるため維持しています。
- 在庫切れ・訪問済みスポットへの経路生成とStateの値コピーは維持しています。最大8台の長時間の性能・メモリ評価は未実施です。
- 役割提出の独立した締切はAPIにありません。startsAt=0では既存補給範囲内の候補を即時提出します。既知startsAtから独立した役割締切を保証することはできません。
- ブランドは公式実績APIから取得できず、受理された計画の再生値です。
- 期限チェックは後処理時間を含む厳密な実時間上限を保証しません。
- 公式配布物にはゲーム処理のソースがありません。本番サーバーへの接続、全公式マップ、勝率比較は未実施です。
